## The defect the click-through found

`invoice.paid` arrived **80ms before** `checkout.session.completed`:

```
04:18:43.553  invoice.paid               <- carries the period end
04:18:43.561  unknown_subscription       <- no row yet, event DROPPED
04:18:43.633  checkout.session.completed <- creates the row, no period end
04:18:46.281  settle:cs_test_...         <- idempotent, no duplicate
```

A Checkout Session payload has no `current_period_end` and no `items`, so the row is created
with `None` and the UI shows "Active" with no renewal date. Only the nightly reconciler fixes
it — the `reconciled_drift` incidents for users 5 and 7 are exactly this, so it is
reproducible, not a fluke. Logged in `ISSUES.md` rather than fixed on the spot (D10); it needs
its own D1 slice.

This is the argument for click-throughs in one example: 479 backend tests and 363 dashboard
tests are green, `billing` is at 100% line+branch, and none of them caught it — because the
race only exists between two real webhook deliveries.

## Decisions made (link ADRs)

- **[ADR-0027](../../adr/0027-playwright-e2e-harness.md) — the e2e harness exists, is scoped
  to identity, and mirrors the production subdomain topology.** Amends ADR-0021 clause 3 and
  ADR-0026's D3 table. Blocking from day one with a deliberately small suite, because a
  non-blocking gate is one nobody fixes; retries are 1 in CI and a retry-pass is a finding,
  because retries as a flakiness cure turn an intermittent real bug green.

- **[ADR-0026](../../adr/0026-coverage-ratchet-not-aspirational-100.md) — coverage is a
  ratchet floor CI enforces, not an aspirational 100%.** Partially supersedes ADR-0021's
  clause 1. The floor may only go up; **lowering it requires an ADR**. 100% stays the target.
  ADR-0021's e2e clause is explicitly marked **not yet in force** — no Playwright harness
  exists anywhere — and `CLAUDE.md` D3/D9 now say so.
  - The honest framing: this **lowers the stated standard** (100 → 92/97). It trades a number
    nobody enforced for a smaller one everybody does. Recorded as a retreat, not as progress.
  - Root cause worth remembering: the gate stayed off for three months because turning it on
    would have failed every unrelated PR, so the honest answer was always "not this PR". A
    gate whose entire adoption cost lands on whoever touches it next never gets adopted.
    Setting the floor to *what already passes* makes adoption free.

## 2026-09-04 (later) — the security gate runs, and it found something real

ADR-0030 wires `gitleaks` and `pip-audit` into CI as blocking checks and Lighthouse into a
nightly workflow against staging. This was the oldest un-run gate in the project: the
Definition of Done has asked for a security pass and a performance budget since
2026-06-17, and until today the answer was a human saying "reviewed manually" at handoff.
Third time this project has found the same shape — coverage (ADR-0026), e2e (ADR-0027),
now this.

**The first run paid for itself in one command.** `gitleaks` over 439 commits returned 13
findings. Nine are the old MVP's `.envs/` committed wholesale in April: an `sk_live_`
Stripe secret key, an AWS `AKIA` access key *and* its secret, the Django `SECRET_KEY`,
Postgres and Flower passwords. Deleted from the tree, kept by history, on GitHub. Rotation
is now next action #1 — a scanner cannot un-leak anything. Four more were a stray
`portal-snapshot.md` at the repo root: a Playwright accessibility dump from yesterday's
billing click-through, carrying a Stripe test-mode portal session secret. Deleted.

**Allowlisted by fingerprint, not by rule.** `.gitleaksignore` carries one annotated line
per historical finding, so a new secret in a new commit still fails while the known
exposure stays legible. Disabling the `generic-api-key` rule would have been one line and
would have blinded the gate; rewriting history would have broken every SHA quoted in
`docs/` and every submodule pointer, and would still not have revoked a single key.

**Everything was validated locally before the PR** — gitleaks green with the ignore file
and red without it, `pip-audit` clean on the production dependency set in an isolated
venv, `lhci autorun` green against real staging over 3 runs × 2 URLs. Setting a threshold
without measuring first is how you ship a gate that is red on day one and muted by day
three.

**pip-audit is scoped to production dependencies only.** A CVE in `pytest` cannot reach a
user, and a gate that goes red for something harmless teaches people to click past it.
Same reasoning as the e2e table: narrow and honest beats broad and ignored.

Lighthouse floors are ratchets set to measured values (ADR-0026's sense), and the four
audits that keep the categories off 100 — no meta description on marketing, contrast and
console errors and an invalid `robots.txt` on the dashboard — went to `ISSUES.md` rather
than being fixed here (D10).

**Executing the plan found two defects in the plan.** This is the argument for writing plans
detailed enough to be wrong in specific ways.

- Its model tests created a `Subject` with slug `quran` — which the very next task seeds. They
  would have started failing on a duplicate the moment that migration landed.
- **Its `seed_e2e` task was impossible.** It had identity's seed command reset the teacher's

  `curriculum.models` was forbidden. But `identity imports no other business modules` bars
  importing `kaleem.curriculum` *at all*. I had noticed half the contract and written a fix
  that trips the other half.

The fix for the second is better than the plan anyway: the e2e specs converge their own
fixture. Each clears the set, sets exactly what it wants, and asserts the *exact* state —
deterministic no matter what a previous run left. Verified by running the suite twice, the
second time against a database the first run had dirtied. Asserting merely "Quran is checked"
would have passed vacuously.

**Two more things the code told me, not the plan.**

Ruff rejected the test I wrote to cover the abstract base view's stubs (`SLF001` private
access, `PLC0415` local import) — and it was right. I was writing a test for code that
existed only because of my design. Deleted the base class; two explicit views duplicate three
lines per verb and name the table they touch. `curriculum` is 100% line and branch with no
`pragma: no cover`.

And Biome rejected `<SubjectsCard role="teacher" />`: a prop literally named `role` on a JSX
element reads as the ARIA attribute. Renamed to `audience`. A lint rule catching a naming
collision I would not have noticed in review.

## 2026-09-05 (later) — the keys are rotated, and a documented rule turned out to be wrong

The `588a1e35` credentials are rotated: the `sk_live_` Stripe key, the AWS access key and
secret, the Django `SECRET_KEY`, Postgres and Flower. That was the only *active* exposure on
the whole backlog, open since the first gitleaks run found it on 2026-09-04.

**Then the bookkeeping refused to work.** ADR-0030 clause 2 ends "Removing a line is how a
rotated credential gets recorded as dealt with," and `.gitleaksignore`'s own header says "an
empty file is the goal." Both are wrong, and wrong in a way that would have gone unnoticed
until the next CI run: **rotation makes a credential dead, not absent.** The strings are
still in git history and still on GitHub — `git show 588a1e35:kaleem/.envs/.production/.django`
still prints them. Delete the fingerprints and gitleaks reports them again, on every branch,
forever. The only way to empty the file legitimately is a history rewrite, which the same ADR
rejects two sentences earlier.

So ADR-0030 contained a rule that could not be followed without breaking the gate it created.
ADR-0032 amends it: a rotated credential keeps its fingerprint and gets re-annotated with the
rotation date. The allowlist stops being a to-do list and becomes a rotation record.

Worth noticing *how* this surfaced. The instruction was three words — "all keys rotated" —
and the obvious next move was to do what the docs said. Reading the docs against the actual
state of git history is what caught it. A rule written at the moment of discovery, when the
credentials were live and rotation was hypothetical, did not survive contact with the day
rotation actually happened.

Also corrected `STATE.md`'s `last_green_ci`, which still pointed at meta #146 from the day
before, and the two cross-references that pointed at the now-deleted rotation entry.

## 2026-09-05 (later) — Phase C1: matching, spec to PR in one session

Specced, planned and implemented C1 end to end: **broadcast to every eligible teacher, first to
accept wins, result is a durable `TeacherAssignment`.** Three PRs open — backend#42,
dashboard#35, and the meta pointer bump. Nothing merged yet.

**The decision the design turns on: offers are not rows.** A teacher's inbox is computed live
from open requests minus that teacher's declines. A materialised offer table would go stale the
moment a teacher added a subject or edited availability, and the spec's promise — an unmatched
request is re-evaluated when the pool changes — would then need a job to re-fan-out. Computed,
it is a property of the query. `test_a_request_with_no_eligible_teacher_stays_open_and_becomes_matchable`
exists to make that regression loud: it asserts a teacher who qualifies *afterwards* sees the
offer with nothing re-run in between.

Ran it as 14 plan tasks, each implemented by a fresh subagent and gated by its own review, then
a whole-branch review at the end. **Eight defects surfaced, and most of them were in the plan
rather than the code** — which is the useful finding. Writing the plan out in full, with the
actual code in it, is what made them findable by a reviewer who had never seen the spec.

The two worth remembering:

- **`_student_preference` failed open.** It returned `NO_PREFERENCE` when a student had no
  profile, and `NO_PREFERENCE` is the *most permissive* branch — it admits every teacher,
  including one whose own gender is undeclared. So "we do not know this child's preference"
  meant "any teacher will do": exactly the wildcard C0's gender rule forbids, reached through a
  different door. Unknown must fail closed, and now does, on both the inbox and the accept path.
- **`SubjectsCard` discarded unsaved edits.** Its `useEffect` re-seeded checkbox state from

  for months because the e2e student had no subjects, so stomping an empty response changed
  nothing visible. C1's fixture gave that student a subject and the bug became deterministic,
  turning `subjects.spec.ts` red. Fixing the component rather than making the spec wait was the
  call: waiting would have gone green while hiding a defect a real user can hit.

**Two process notes.**

The coverage ratchet nearly bit. Raising `fail_under` to `97.2` would have turned CI **red** —
coverage.py rounds the measured total to `precision` decimals before comparing, and with the

## 2026-09-05 (later still) — Phase C2: booking + quota

Specced, planned and implemented C2 in the same session as C1: a student claims a standing weekly
slot, a daily idempotent job materialises the cycle's sessions up to quota, and either side can
cancel — 24 hours ahead returns the unit, and a teacher's cancellation always does. Three PRs open.

**`sessions_per_cycle` has been on the plan model since July and nothing had ever read it.** A
parent could buy four sessions a month and receive none. That is the hole this closes.

**The find that mattered was not in C2 at all.** Building it, an implementer hit `ProtectedError`
deleting a student, stopped, and asked rather than working around it. I reproduced it: **account
deletion has been broken in production for every student who was ever matched.**
`TeacherAssignment.source_request` was `PROTECT`, and Django's collector evaluates `PROTECT` per
cascade branch without deferring long enough to notice the protecting row is itself being deleted
by a sibling branch. The GDPR erasure task sitting under *Blocks launch* would have walked straight
into it. Both that field and C2's new `Session.slot` are now `RESTRICT`, which still refuses an
orphaning delete but permits a same-operation cascade.

Worth recording that I got the reasoning wrong twice on the way there. I kept `Session.assignment`
as CASCADE because "TeacherAssignment cascades fine from User" — it did not, that *was* the bug —
and kept `Session.slot` as PROTECT because "nothing hard-deletes a RecurringSlot" — untrue, since
deleting a user does, transitively. Both conclusions survived; both premises were false. The ledger
records the falsified reasoning next to the correction, because the next person to read those two
`on_delete`s will otherwise rebuild the same wrong model of them.

**What green tests did not catch.** Three defects this phase would have shipped behind a passing
suite:

- A test that **fails one day in seven**. The refill test cancelled "a far-future session" that was

  Saturday morning. It passed on the day it was written.
- A fixture change of mine that **broke a suite in the other repository**. Making the seed

  report. One student cannot be both unmatched and booked — so there are two students now.
- A **teacher seeing a red error box** on `/schedule`, because `QuotaBadge` rendered

  hook it was handed. Only a real browser with a real teacher session showed it.

**And a file that documented a rule it did not enforce.** The final review found `DELETE /slots/`
was never given the student gate my own ruling ordered — while the comment written to record that
ruling asserted it had been. The deferred "no API-layer 403 test on that view" was exactly why it

**One root cause, three symptoms.** Multi-subject booking refused, parents unable to claim, the

## C3a — video rooms, and no video

Phase C3 was going to be a Zoom adapter. It is not: the user chose to build kaleem's own 1-on-1
WebRTC service, which reverses ADR-0011 and cost **group sessions their place in v1**. ADR-0034
records both, along with the two things the reversal makes mandatory and neither of which exists
today — a TURN server (roughly one connection in six cannot go peer-to-peer and fails outright
without a relay) and ASGI/Channels for signaling, which production does not serve.

Two facts made the reversal cheaper than ADR-0011 priced it. Zoom's free tier caps *every*
meeting at 40 minutes against kaleem's 60-minute lessons, so the "free" v1 path never existed.
And the 6–12 month estimate priced an SFU with group and recording; restricted to 1-on-1, media
goes peer-to-peer and the backend reduces to signaling plus authorization. That is a different
engineering category. So video became five slices, and **C3a deliberately contains none of it** —
the room lifecycle, the authorization guarding it, and the provider seam are identical whether
media ends up P2P, an SFU, or a vendor, so they ship first behind a fake.

**The spec I wrote was wrong twice, and the plan caught it.** Writing the plan meant reading the
code the plan must name, which surfaced both: I had specified a 503 where `platform/drf.py` maps
`ExternalServiceError` to **502** (and documents why — 503 claims kaleem itself is down), and I
had promised "a distinct typed code per failure" when the API error body is `{"detail": ...}` with
no code field at all. The second correction changed the design rather than a constant: the
countdown is now driven by `can_join_at`, so a well-behaved client never provokes the window
error, and the 409 is a backstop for a stale tab rather than control flow.

**What green tests did not catch — five, this time, all the same species.** Every one was a test
that looked like coverage without being coverage:

- **The row lock was untested.** The "one room per session" test made three *sequential* calls and
  passed with `select_for_update` deleted — while the spec named concurrency as the primary guard
  and the unique index as merely the backstop. It now takes real threads, a barrier, and a
  deliberately slow provider; removing the lock produces a genuine `IntegrityError`.
- **The lock was also far wider than recorded.** `select_related("assignment__subject")` means
  Postgres locks the `Subject` row too, and there are about three subjects platform-wide — so one
  student joining a Quran lesson would have serialized every Quran join once a real provider does
  I/O. I had already accepted a deferral on this, with a bound wrong by orders of magnitude.
  Both mitigations were one line each, so the right move was to stop deferring it.
- **A teacher who is also a parent would have seen no Join button** on lessons they teach. The
  parent guard reused `resolveViewerRole`, a display heuristic where "parent wins" is correct for
  choosing which names to show and wrong as a capability gate. Now server-computed per row.
- **The seed's idempotence test could not detect the bug it existed to forbid.** The command resets
  the student's rows every run, so "run it twice, count is stable" passes whether the code
  repositions a session or creates an extra one. Pinning the count *within* one run against the
  plan's quota is what distinguishes them.
- **The countdown said "Opens in 19791 min."** Unit tests only exercised times near the boundary;
  the e2e asserts only disabled-versus-enabled, never the label. Sessions generate weekly for a
  whole cycle, so *most* rows looked like that. Found in a browser, in the D9 walk, which is
  precisely what that step is for.

**A false claim of my own.** I recorded that I had verified the dashboard suite against raised
coverage floors. I had verified the working tree; only one of four floors was ever committed. The
verification was real and ran against a file that was not in the branch. The final review caught
it. Worth remembering that "I checked" and "the branch contains it" are different statements.

**One duplication I refused to carry.** Two functions restated "the actor is this assignment's
teacher or student". Normally a deferred minor — but one gates entry to a video call with a child
and the other decides whether the UI offers it, so a future widening that updates one and not the
other fails silently onto safeguarding. Widening is now one line in one place.

Backend 753 at 98.16% (floor 97.3 → 98.1); dashboard 543 at 93.63/90.48/86.69/93.63 (floors →
93.5/90/86.5/93.5); e2e 30 → 33. Verified by hand as a student in English, a student in Arabic
with RTL, and a teacher.

opens a tab at a host that does not resolve. That is C3a finished, not C3a broken.

## C3b — signaling, and the bug a green suite could not see

Phase C3b split signaling into its own service — escape hatch **E5**, which the roadmap marks
*"not pre-approved… requires a full ADR with evidence."* Half its trigger genuinely fits (long-lived
connections are the shape a WSGI monolith handles worst); the other half does not (no production,
no users, no measured pain). **ADR-0035 says the evidence is architectural rather than observed**
rather than dressing it up, because a reader in six months should find the weakness written down
instead of reconstructing it.

The split earned one thing immediately: a separate process cannot ask the database whether a grant
is genuine, so C3a's forgeable token had to become HMAC-signed and verified. That closed a
*Blocks launch* entry as a **precondition** rather than a someday.

**The finding that matters.** The final whole-branch review ran the service under real uvicorn —
something no test does — and found the capability token written to the log on every single
connection:

```
INFO: "WebSocket /ws/rooms/session-42?t=eyJleHBpcmVzX2F0IjogMTc4ODY0OTc1M…OEE" [accepted]
```

A live grant to one child's video room, sitting in `docker logs` for its full thirty-minute life,
replayable by anyone who can read them. `--no-access-log` would not have stopped it (different
logger). Ninety-two signaling tests were green throughout, because **every one of them runs
in-process through Starlette's `TestClient`** — uvicorn, Traefik and TLS are all below the layer the
suite touches, and the bug lived exactly there. I reproduced it myself before accepting it, and
again after the fix.

Chasing it turned up a second: Traefik's access log carried the token too, its `redact` option is
**silently ignored** for core field names, and it has no per-router configuration. So the choice was
a gateway that logs capability tokens or a gateway that logs no paths at all. We took the second and
compensated with gunicorn's own access log for the API — a real, platform-wide observability loss,
recorded rather than glossed. The actual fix is to move the token out of the URL entirely; that is
C3c's, and it is filed.

**Eight findings, one species.** Across C3a and C3b nearly every review finding has been the same
thing: a test or a comment that reads as a guarantee and is not one. A docstring contradicting its
own error messages. An unreachable branch. A test whose *name* said "unknown room" while its body
used a full one. A malformed-token test whose five cases were all ASCII — so the `TypeError` crash
its name promised to prevent was the one case it never tried. A contract whose comment claimed it
forbade Django while its list held only eleven `kaleem.*` modules, so `import django` passed CI
green. Bad-message tests that accepted *any* close code, when three distinct codes are the entire
point. A "no email in the URL" assertion that could not fail because no email ever went near the
URL. The suite is not what caught these. Review was, every time.

**A ratchet held.** Bringing `signaling/` into coverage for the first time dropped the total to
97.59 against a 97.6 floor, and the honest options were to test three error paths or write an ADR
lowering the ratchet. Lowering would have recorded our own omission as the new normal, so we tested
them — including the one that proves a peer whose socket dies does not take the surviving call
with it. Coverage finished at 97.78 and the floor went **up**.

**Two of my own corrections.** I reported `httpx` as "already installed but undeclared"; it was
residue from a subagent's throwaway `pip install` in a container a rebuild later replaced — the
ruling to settle it by rebuild rather than argument was right, the reason I gave was reading state
that was not real. And I demanded a test for a property that **cannot be tested** (a join to a
non-existent room can never be refused), which cost a round and produced a name/body mismatch from
an implementer trying to satisfy an impossible instruction.

Backend 852 at 97.78%; `lint-imports` 11 kept / 0 broken, the new contract broken deliberately in
**both** directions; e2e unchanged at 33 and said so in the D3 table rather than quietly claimed.
Walked by hand over real sockets: presence, relay, departure, and every refusal code.

**What ships is a relay with no client.** No browser code, no TURN — so no call connects, and
roughly one in six will need a relay even once C3d exists. That is C3b finished, not C3b broken.

**Shipped and verified on staging the same day.** `deploy-staging` succeeded on the first attempt
because the VPS `.env.production` was edited before the merge landed, which is the one thing that

`{"status":"healthy"}` over a valid certificate, so the deployed secret is present and usable.
It still does not prove the API holds the *same* secret; nothing in the deploy can, and the first
real proof will be a successful join once C3d exists.

## C3c — STUN/TURN, and three hardening items (2026-09-06)

**Code-complete and reviewed, but nothing has shipped yet.** Four PRs are open
(backend#46, infra#7, dashboard `feat/phase-c3c-ice-schema`, meta `feat/phase-c3c-turn`); none
are merged, and coturn is not deployed anywhere. What this phase built: a self-hosted `coturn`
relay, HMAC-derived ephemeral credentials delivered to the browser as `ice_servers` on the
existing join grant, and three things riding the same grant and the same deployable — the
capability token moved out of the URL query string into `Sec-WebSocket-Protocol`, a room now
pinned to one deploy colour, and `GRANT_TTL` deleted. Live verification (`turnutils_uclient`
plus the throwaway relay-only `RTCPeerConnection` harness) is **outstanding**, blocked on the VPS
DNS/firewall work only a human can do — see `STATE.md`.

Backend 881 at 97.76%; dashboard 545 with floors ratcheted to 93.6/90.4/86.6/93.6; e2e unchanged
at 33 and recorded as `❌ by design` in the D3 table rather than quietly claimed. `ruff`, `mypy`,
`lint-imports` and `makemigrations --check` all clean.

**The plan contained a Critical, and an implementer caught it.** The `turnserver.conf` I wrote
had `static-auth-secret=${TURN_SECRET}`. **coturn performs no variable expansion in its config
file**, so that sets the shared secret to the literal string `${TURN_SECRET}` — not a broken
deploy but an *open relay*, with a publicly guessable secret letting anyone mint credentials and
use kaleem's relay as a proxy and a DDoS amplifier. It would have passed every gate: there is no
test suite in `infra`, `docker compose config` resolves happily, and coturn starts. The fix is to
pass it as a CLI argument, which Compose *does* expand. The lesson is not "review configs" — it
is that **a config language's non-features are invisible to every gate we own**, and the only
thing that would have caught this is the live `turnutils_uclient` check the spec already
mandated. The subagent raised it as a mild "worth a smoke test"; the severity was mine to assign.

**`ISSUES.md` promised a fix that does not exist, and C3c withdraws it.** C3b dropped Traefik's
`RequestPath` from the access log because it carried the signaling token, and recorded that the
field could be restored once the token moved. It cannot. `config/urls.py` includes `allauth.urls`,
which serves `/accounts/confirm-email/<key>/` and `/accounts/password/reset/key/<uidb36>-<key>/` —
single-use **account-takeover** credentials in the **path**, not the query string. Moving one
credential out of one query string changed nothing about whether logging paths is safe. Dashboard
and marketing get their path-level visibility from their own container access logs instead. Worth
noting how the wrong belief survived: it was written down as a plan, and a plan in `ISSUES.md`
reads as a decision rather than a hypothesis.

**The split-room fix in `ISSUES.md` was also incomplete.** It proposed per-colour WS hostnames so
a room could not straddle a deploy. But `django-blue` and `django-green` both claim
`Host(${API_DOMAIN})` too, so two participants could be served their grants by *different Django
colours* and straddle anyway. Hostname pinning narrows the window; it does not close it. The
actual fix is `Room.signaling_url` — the colour becomes a property of the room, written by the
first joiner under the session row lock that C3a already added, replayed to everyone after. The
trade is deliberate: a room pinned to a stopped colour now fails a rejoin **loudly**, where before
it silently succeeded into a split room.

**The coverage ratchet did not move, and that is the honest outcome.** Measured 97.76%. Tried
`fail_under = 97.8` and it failed — "Required test coverage of 97.8% not reached. Total coverage:
97.76%" — even though the report *displays* `97.8%`. So `pyproject.toml`'s comment about
`precision = 1` rounding the total before comparison describes a rule coverage.py does not appear
to follow. Reverted to 97.7 and logged the contradiction rather than leaving a knife-edge floor;
this project has been bitten twice by exactly that.

**Also found:** there is no `docs/architecture/scheduling.md`, and there never has been. C0, C1,
C2, C3a and C3b each silently skipped that line of D9. `scheduling` is now the largest module in
the codebase. Logged rather than faked — a TURN-only architecture doc would misrepresent the
module more than its absence does.

**What ships is still not a call.** C3c has no browser code. `RTCPeerConnection`, the video grid
and the controls are C3d, which is the first phase that can produce a working call. What exists
now is a relay, credentials for it, and a signaling handshake that no longer leaks its own
credential.


### C3c shipped and verified the same day — and the deploy found four more defects

**The relay works.** First media path ever to traverse kaleem's infrastructure: a relay-only
`RTCPeerConnection` pair in a real browser connected through coturn on staging — data channel
open, 2289 bytes sent / 2434 received, candidate `46.225.151.255:49195`, inside the configured
49152–49999 range. **Mutation-checked**: one extra character on the secret gives `401
Unauthorized` and zero relay candidates.

**The signaling handshake was verified over real sockets**, all four cases: a valid token in
`Sec-WebSocket-Protocol` connects and the server echoes `kaleem.signaling.v1` (never the token);
a tampered signature, a protocol-name-only offer, and a no-subprotocol connection each close
4401. Critically, the first three keep the selected subprotocol while the fourth reports an empty
one — which is the pre-flight ruling about RFC 6455's *mirror* violation, working in production.
No token appears anywhere in the signaling or Traefik logs; only the refusal reasons do.

That handshake test also proves something the health check explicitly cannot: **the deployed
Django secret and the signaling secret match.** A successful join is the only evidence of that,
and until now none existed.

**Four defects were found between "reviewed" and "running", none by any test or review:**

1. **`coturn` was missing from `ship.sh`'s shared-services list**, which is explicit — so the
   deploy would never have started the relay. Every join would have handed out ICE servers for a
   host that does not exist, silently.
2. **CI did not sync `coturn/turnserver.conf` to the VPS.** Docker would then have created an
   empty *directory* at the bind-mount path, and coturn would have run with no deny-list and no
   quotas: an unfenced relay on raw UDP.
3. **coturn rejects CIDR in `denied-peer-ip`.** `fe80::/10` and `fc00::/7` logged `ERROR: Wrong
   address format` and were skipped, leaving the IPv6 half of the SSRF fence open while looking
   correct. The final re-review had explicitly asserted no directive would be rejected at startup.
   Running the image is what disproved it.
4. **Removing `no-stdout-log`/`syslog` did not restore logging.** coturn's default sink is a
   *file inside the container*, so `docker logs` stayed empty. Needed `log-file=stdout`.

The pattern is uniform and worth naming: **every one of these lived in the gap between a config
file and the process that consumes it** — a list that must be edited by hand, a file that must be
copied, a syntax the parser silently rejects, a default that overrides an omission. Nothing kaleem
owns tests that gap. The only thing that found them was running the real binary and reading its
output, which is precisely the `turnutils_uclient`/relay-harness step the spec insisted on.

Two self-inflicted stumbles worth recording: my own pre-flight created `/opt/kaleem/coturn` as
root, which made the deploy's `scp` fail with `Permission denied` (loud, safe, one `chown` to
fix); and I misread GitHub's UTC timestamps against a local UTC+3 clock, concluded a job had been
queued for three hours, and cancelled a perfectly healthy pipeline. Check the timezone before
declaring something stuck.

### C3d (the call client) — code shipped and tested, phase not yet closed

**What shipped.** Backend#47 (`is_teacher` on the join grant) and dashboard#39: a full-bleed
route `_call/sessions/$sessionId/room`, a mandatory lobby, three hooks (`useLocalMedia`,
`useSignaling`, `usePeerConnection`), and a call room with mute/camera toggles and a leave
control. Dashboard: 645 unit tests, 95.3% statements / 91.5% branches / 87.4% functions / 95.3%
lines (floor 93.5/90/86.5); e2e 33 → 35 flows, both new ones exercising a real two-peer call —
one asserts both sides see a remote track producing frames, the other asserts one side leaving
abruptly is seen by the other.

**State it precisely: this is not the same as "the call feature is done".** CI has no coturn, so
the e2e proves host-candidate peer-to-peer connectivity only — the relay path stays covered by
C3c's one-time live verification, not by anything that runs on every merge. And fake media
proves plumbing, not quality: nothing in CI can tell whether audio is audible or video is
watchable. The live manual check (Task 10) has **not** happened yet. Both limits are written
into the D3 table row in `CLAUDE.md` and into `docs/runbook/video-call.md`, in the row itself,
not as a footnote.

**A bug the unit suite structurally could not see.** `usePeerConnection`'s tests covered the
offer rule, the answer path, ICE restarts, and state mapping — and every one passed while the
call carried no media at all. The cause: `peer-joined` triggered `createOffer()` immediately,
but track attachment happened in a separate effect gated on a second, independent
`getUserMedia()` call. When the peer announcement arrived first, the offer described zero
media, yet `connectionState` still reached `"connected"`. The test double made this
unrepresentable, not just untested: `localStream` was `null` in every test, and the fake
`RTCPeerConnection` has no concept of media at all, so "the offer describes no media" wasn't a
condition any assertion in that suite could ever phrase. Every assertion was about which
message got sent, never about what was in it or what had to happen first. The fix
(`tracksAddedRef` + a deferred-action queue, later generalised to `runOrDefer`) was found by
running the real stack end to end, not by the suite going red.

The same race turned up a second time on the answer path during review: an offer arriving
before the student's own `getUserMedia` resolved produced a `recvonly` answer that nothing ever
renegotiated — a call that looked connected and stayed one-way forever. Both instances are now
guarded by the same `runOrDefer` choke point, and both have dedicated unit tests plus a
regression test for the exact race shape requested in review.

**A mutation check that was wrong the first time, for an instructive reason.** The brief asked:
break the single-offerer rule and confirm the e2e goes red. The first attempt flipped one of
*two* places that rule lived (the immediate-offer guard; a second identical guard survived in
the deferred-offer flush), so the "conclusion" that both offering is harmless was actually a
mutation that changed nothing observable. Redone with the guard properly collapsed to one
location and genuinely flipped, the call **still visually completed** — not because two
offerers are safe, but because the signaling server notifies existing peers before the newcomer,
which deterministically gives one side's offer a head start in this exact two-party setup. The
losing side's own delayed offer then throws a real, unhandled `InvalidStateError` on
`setLocalDescription` — the connection is genuinely in the wrong state, it just doesn't fail
loudly under this specific message ordering. That gap was closed by asserting no `pageerror`
fires in the e2e spec, which does turn red under the mutation. Recorded honestly rather than
buried: that `pageerror` assertion is only durable while nothing anywhere `.catch`es the
rejection it depends on surfacing — the real, load-bearing pin for the single-offerer invariant
is the unit-level call-count tests, not the e2e check layered on top.

**Left unsolved, logged rather than fixed (D10):** no Safari/iOS support yet (tracked to C3e,
ADR-0034); device changes mid-call aren't handled; device choices aren't remembered between
lessons; `useLocalMedia`'s `selectCamera`/`selectMicrophone` update state but never re-acquire
the stream; and the e2e gate's structural inability to see the relay path. Full entries in
`ISSUES.md`.

### C3d verified live — a real call, through the relay (2026-09-07)

**It works.** A two-peer call on staging, forced `iceTransportPolicy: "relay"` so every packet had
to traverse coturn: both remote tracks arrived, both peer connections reached `connected`, and the
succeeded candidate pair carried **443 KB sent / 455 KB received** of real media on candidate

`kaleem.signaling.v1` and both grants named the same colour-pinned host. That is the whole

**CI caught something no local run could, and it is the lesson of the day.** `e2e/call.spec.ts`
passed locally and failed in CI on both attempts. The cause: the `e2e` job never ran the signaling
service and never set `DJANGO_VIDEO_PROVIDER`, so it fell back to `FakeVideoProvider`, whose

only ever run locally under a `docker-compose.override.yml` that was created for the run and
deleted afterwards, and CI was never made to match.

That is the same failure this phase produced five times over, one level up: *the thing that
verifies is itself unverified.* A green suite hid a call with no media because the double could
not represent media. A green local e2e hid a pipeline that could not run it, because the
environment was hand-made and then thrown away. **The environment is part of the deliverable**, and
"it passes on my machine with a file I deleted" is not a gate.

**The final review found a Critical that came from the spec, not the code.** `inset-t-*` and

compiling the classes against the repo's own Tailwind. Worth repeating: **for CSS, the only
verification that counts is compiling it.**

### C3e-a shipped — a channel for the failure we cannot reproduce (2026-09-07)

**What shipped.** `POST /api/v1/scheduling/sessions/<id>/diagnostics/`, authorized by the same
`rooms.is_participant` predicate the join guard uses, over a closed eight-code vocabulary — an
unknown code is a `400` and writes no row. `user_agent` is read server-side from the request
header, never trusted from the body. WebRTC stats are redacted client-side by an **allow-list**,
not a deny-list: named fields are copied out of each stats entry and everything else is dropped
by construction, so a field a future browser adds cannot leak an address just because nobody
here knew to name it. Retention is 90 days via a Celery beat job. Four emitters are wired to
failures the code already detected — three `getUserMedia` classifications plus
`autoplay-blocked`, which used to be `video.play().catch(() => {})`: a perfectly silent failure
that, on Safari, reads to a parent as "the teacher isn't talking." That empty catch becoming a
report is worth the endpoint on its own.

Backend: 902 tests passed at 97.78% (`fail_under` stays 97.7 — rounds the same under
`precision = 1`). Dashboard: floors raised to 95.2/91.5/87.0/95.2 lines/branches/functions/
statements, measured 95.37/91.64/87.16/95.37. e2e: `call-diagnostics.spec.ts` adds 2 flows
(35 → 37) — a contract test that POSTs every code the client's own array holds through the real
endpoint and asserts 201, plus a check that an unknown code is refused.

**Why diagnostics shipped before the Safari fixes, and it is the whole point of the phase.**
C3e exists because Safari and iOS are untested and this project has **no access to any Apple
device** — no Mac, no iPhone, no iPad — and Playwright's WebKit on Linux is not iOS Safari and
has no fake-media equivalent. Before this endpoint, a Safari user whose call failed produced
exactly one signal: a parent saying "the lesson didn't work," compatible with at least six
distinct defects. Shipping the seven C3e-b hardening fixes first would have meant seven
behaviour changes, on a browser nobody here can run, with no channel to discover whether any of
them worked — precisely the failure this phase keeps repeating (C3b's logged token, C3c's five
unfound-by-test Criticals, C3d's fake-media suite that couldn't represent a call with no media):
**something fails, the code carries on, and nobody is told.** This endpoint is the fix for that,
applied to the one browser this project cannot verify by any other means.

**The single most important decision is the allow-list, and it is dangerous in a specific way
worth restating.** The obvious implementation of "strip the IPs" is a deny-list — delete
`address`, `raddr`, `ip`. That is wrong precisely because `RTCStatsReport` fields differ per
browser and version, and Safari is exactly the browser whose stat shape cannot be inspected from
this project. A deny-list leaks every address-bearing field nobody here knew to name, and the
browser most likely to have one is the browser this whole phase exists for. The allow-list's
test uses a realistic Safari-shaped fixture with genuine dotted-quad and IPv6 addresses and
asserts none survive — a two-field stub would have removed the constraint under test.

**D9 deviation, recorded rather than skipped.** The Definition of Done requires a manual browser
click-through, and no click-through on Safari or iOS is possible in this project — there is no
device to click through on. C3e-a is the one slice of this phase that can still close cleanly
under D9 by every other measure (spec, plan, TDD, coverage floors raised, boundary check green,
e2e green on Chromium), because the pipeline itself does not care which browser reported to it.
The click-through step is the one D9 cannot get here, and that gap does not close in C3e-b
either — C3e-b will have the identical problem for its seven fixes.

**What this does not prove, and the verification loop that replaces a test.** The pipeline is
verified on Chromium; that Safari emits anything through it is not verified and cannot be
verified here. The e2e drift guard is also directional: it proves the client knows no code the
backend rejects, but not the reverse — a code added to the backend enum with no client emitter
would sit as dead weight, unnoticed, because the guard only ever POSTs codes the client's own
array already holds. Accepted: an unused enum value is not a production failure the way a
rejected request is. Once C3e-b ships its fixes, the actual verification loop is watching each
code's row frequency fall over the following weeks — slower and weaker than any test, and the
honest substitute for one that cannot exist here.

Energy: 3.


### C3e-b code-complete — seven fixes, none verified on the browser they exist for (2026-09-07)

**What shipped.** Seven defects fixed, all dashboard-only, no backend or signaling change — the
protocol stays closed at `peer-joined`/`peer-left`/`offer`/`answer`/`ice` (C3b):

1. `min-h-dvh` replaces the static-viewport unit on the three call surfaces — `Lobby`,
   `CallRoom`'s terminal screen, and the room route — **and on `__root.tsx`, the container every
   route renders inside**, which the first pass missed and which pinned the document to `100vh`
   regardless of what the call surfaces asked for. Verified by compiling the class, not by
   reading the source: the C3d spec's `inset-b-*` incident (a non-existent Tailwind utility that
   compiled to nothing) is exactly the failure mode a source-text assertion would have missed
   again. The guard now scans all of `src/routes/` and `src/features/call/` rather than three
   named files — a guard that only looks where it was pointed cannot catch the container nobody
   thought to point it at.
2. `getUserMedia` moved behind a tap. `useLocalMedia` no longer acquires on mount; the Lobby
   opens with no preview and a "Turn on camera" control, and `start()` runs
   inside the tap's gesture. **This is a visible product change, not a silent fix** — the Lobby
   gains a step it did not have before, matching how Meet and Zoom behave. A refusal for want of
   activation emits `gum-no-gesture`.
3. A "Tap to turn on sound" control appears over the remote tile when `play()` rejects on an
   unmuted element — the most likely and most silent Safari failure, previously an empty
   `.catch(() => {})`. The tap calls `play()` inside its own gesture.
4. `restartIce()` is feature-guarded (`typeof pc.restartIce === "function"`). Unguarded, it threw
   *inside* the connection-state-change handler, taking out the whole recovery path along with
   itself — the guard's cost is one line against losing reconnection entirely.
5. Backgrounding/screen-lock recovery reuses `RoomPage.handleRetryConnection` rather than a
   second mechanism — `visibilitychange` back to visible is a new *trigger* onto machinery that
   already existed. The trigger fires only when the call **has been up and is now down**, and at
   most three times per page. "Not `connected`" was the first guard and was wrong: `connecting`
   is the normal state for the whole "waiting for your teacher to join" period, so an ordinary
   tab switch during the lobby wait wrote a false `backgrounded` row, re-ran `getUserMedia`
   outside the gesture this same phase added, and churned sockets against a room that seats two.
   The bound is owned by the route because the recovery *remounts* `usePeerConnection`, resetting
   its own `MAX_ICE_RESTARTS` to zero every time. The teacher's side needed no protocol change:
   `peer-left` or a stalled connection already exist, only the copy ("their connection dropped —
   waiting for them to come back") needed to make what a teacher sees actionable rather than a
   frozen tile. A sixth signaling message announcing "I am backgrounding" was considered and
   rejected — it reopens a deliberately closed protocol and is best-effort anyway, since a hard
   suspend may never send it.
6. Device changes are hot-swapped via `sender.replaceTrack()` — no renegotiation, same `m=` line,
   same codec, so the single-offerer rule is untouched. A deliberate choice (Lobby pick, or a
   persisted one) outranks a newly-arrived device unless the in-use device vanishes, in which case
   it always swaps. Emits `device-lost` when a device disappears.
7. Camera/microphone choices persist in `localStorage` per kind; a stored id absent from
   `enumerateDevices()` falls back to the default silently — a camera used last week must never
   block joining today's lesson.

Dashboard coverage floors raised 95.2/91.5/87.0/95.2 → 95.5/91.6/87.2/95.5, measured

## 2026-09-07 (later still) — shared signaling: a colour flip made a room permanently unjoinable

**What broke.** Merging the session UI redesign flipped staging green → blue, same as any
ordinary deploy. Afterwards `ws-blue-staging` answered fine but `ws-green-staging` returned
Traefik's own `404`, no `server` header — its router was gone. A session whose `Room` row had
been created while green was active, and never ended, now pointed at a signaling host that no
longer existed. Every future join re-read that same dead pin, forever: `_ensure_room` reuses an
`ACTIVE` row rather than minting a new one, so there was no path back to a working URL short of
editing the row by hand.

**Root cause.** C3c's fix for a *different* bug — one room's two participants landing on
different signaling processes during a colour overlap — was to give each colour its own
hostname and have `Room.signaling_url` pin a room to whichever one created it. That pin assumed
the colour it pinned to would keep existing. It doesn't: `ship.sh` stops the old colour's
signaling container on every flip. The C3c fix was correct for the bug it targeted and created
this one as a direct consequence.

**The fix (ADR-0037).** Stop deploying signaling blue-green at all. It becomes one shared
replica — service `signaling`, container `kaleem-signaling-1` — started with the other shared
services (`traefik`, `postgres`, `redis`, `flower`, `coturn`) and never stopped by a colour
flip. `WS_BLUE_DOMAIN`/`WS_GREEN_DOMAIN` collapse back to a single `WS_DOMAIN`. `Room.signaling_url`
still exists and is still written and replayed exactly as before — Task 5 changed zero production
code — but with only one signaling host it can no longer disagree with the live deployment. The
single-replica constraint that room membership is a process-local dict is unchanged; what changed
is that there is now only one process, not one that a room's pin can outlive.

**Two findings worth keeping.**

1. `FakeVideoProvider.create_room` returns a `ProviderRoom` with no `signaling_url` set at all.
   The implementer's first pass at the migration test asserted against the fake provider and it
   would have passed regardless of whether the migration did anything — a vacuous green. Caught
   during implementation, not review: the fix was to point `settings.VIDEO_PROVIDER` at the real
   `SignalingProvider` for that one test so the assertion had something real to fail against. The
   reviewer independently read `fake_provider.py` and confirmed the gap was real. Recorded because
   it's exactly the defect class ADR-0037 itself is about — a seam that looks tested and isn't.
2. With `WS_DOMAIN` unset, `docker compose config` fails with **exactly 3** independent guards
   firing — django-blue, django-green, and the Traefik label on the shared `signaling` service —
   verified by the reviewer running it directly. Three, not one, because `${WS_DOMAIN:?...}`
   appears three separate times in the compose file; any one of them missing is enough to abort
   the deploy before a container starts, which is the point.

**What is NOT verified.** Task 6 — a real staging colour flip, watched end to end — has not run.
It is blocked on two things outside this repo: a DNS record for `ws-staging.kaleem.academy`, and

## 2026-09-07 — the shared-signaling fix, verified live

ADR-0037 shipped and **Task 6 ran**. The fix is verified on the only surface that could verify
it, which was the whole open question when the spec was written.

**What the check was.** Create a room, flip the deploy colour under it, then confirm that room is
still served. Under the old scheme that was precisely the fatal case: `Room.signaling_url` pinned
a room to its creating colour, `ship.sh` removed the old colour's signaling container on every
flip — and Traefik's router lives on that container — so a room created before a deploy named a
host that no longer routed, forever, with `_ensure_room` faithfully reusing the dead row.

**What happened, in order.**

- Migration `0009` ran during the deploy: `0009 applied: True`, active rooms `0`. Every row
  pinned to a per-colour host was ended.
- Green served `SIGNALING_URL = wss://ws-staging.kaleem.academy`, and `_ensure_room` minted room
  id 6 for session 5 at exactly that host — colour-independent, which is the point.
- A second deploy flipped green → blue.
- Room 6, created *before* the flip, was still `active`, and its pin still equalled what the new
  colour serves. `AGREE: True`.
- `https://ws-staging.kaleem.academy/health/live/` returned `http=200 tls=0` before and after.

**The mutation check, which is what makes the above mean anything.** After the flip,
`ws-green-staging.kaleem.academy` returns Traefik's own bare 404 — 19 bytes, no `server` header,
its router gone with its container. `ws-staging.kaleem.academy` answers with `server: uvicorn`.
So a room pinned the old way *would* now be dead, and the one pinned the new way is not. That
contrast is the evidence; the passing check alone would not have been.

**Two things worth recording.**

The DNS blocker never existed. `*.kaleem.academy` is a wildcard — `ws-staging` already resolved,
and a probe for a nonsense subdomain resolves too. Half a day of the spec's "blocked on a DNS
record" was a fact nobody had checked. Worth remembering before writing down a blocker again.

The transition left an orphan. `kaleem-signaling-blue-1` was still running three hours after the
cutover: the new compose no longer defines it, and `ship.sh` no longer stops it, so nothing owned
it. Harmless but unmanaged — an old image holding a live `ws-blue-staging` router. Removed by
hand. Any collapse of per-instance services into a shared one leaves this class of orphan behind,
and the deploy script cannot clean up a service it can no longer name.

**Still not fixed, and still true:** a deploy drops every call in progress. The drain needs a
join-routing switch that does not exist, and "deploy between lessons" stands. Separately, an
operator who edits `WS_DOMAIN` without first ending `ACTIVE` rooms reopens this exact failure for
that one action — documented in the runbook as a required step, and in `ISSUES.md`, rather than
solved in code.

## 2026-09-08 — the session UI redesign, finally looked at

The redesign shipped on 2026-09-07 with a D9 gap I flagged twice and did not close: nobody had
opened it in a browser. Everything proving it was Chromium at two viewport sizes inside a test
harness. This is that check, run against deployed staging as a student.

**It holds.** The desktop card lays out as the three-zone grid it was specced as — time block at
x=297, content at x=380, actions at x=1017, all on one row, both controls 44px tall. The day
heading renders ("Today"). The live state renders: `may_join` true produced the "Happening now"
chip and the accent border. The refund consequence is still on the card, above the fold, before
the cancel control is touched — the thing the spec insisted on twice.

**The reflow is real, and now measured outside a test.** At 1280px the actions container is

same property `e2e/session-ui.spec.ts` asserts, observed on the deployed app rather than a
fixture. Worth having, because the unit tests for this only ever asserted that class strings
were present — jsdom has no layout engine and never proved anything reflowed.

**RTL mirrors with no second rule.** Switched to Arabic: the time moved from x=33 to x=298, the
duration sat to its left at x=247, the chip left of the subject, Cancel right-aligned at x=299,
Join still spanning. Every string translated. The logical-property discipline pays off exactly
as intended, and this is the first time it has been seen rather than inferred from the absence
of `left-`/`right-` in a class list.

**The Lobby's gesture gate holds on the deployed build.** At 844x390 — the short-landscape case
its fix targets — it renders two columns, shows "Turn on camera", and has **no video element at
all**, so `getUserMedia` has not run. That is C3e-b's headline behaviour, alive in production
conditions.

**And it wrote no false diagnostic.** Navigating to the room and rendering the gate produced

Cancel does not, which reads as unbalanced — cosmetic, and invisible to every test we have.
And `slots/` and `quota/` return 404 rather than 403 for a student with no subscription, so
every schedule load logs two console errors; pre-existing and unrelated to this work.

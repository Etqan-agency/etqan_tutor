# Plan 23 — B9b Sign-in (two-factor, phone, quick login) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Requires:** B9a (merged first: this plan reuses its feature-switch, route-table and e2e patterns; no code dependency beyond trunk).

**Goal:** Ship slice B9b: TOTP two-factor with recovery codes, sign-in by phone, login technical fields, admin quick login (impersonation) with a security log, and one-time quick-login links — each off by default — and close allauth's server-rendered account pages.

**Architecture:** All flows go through `/api/v1/identity/` views calling `identity.services` (new modules `identity/signin.py`, `identity/twofactor.py`, `identity/impersonation.py`, `identity/links.py` to keep `services.py` from growing further; `services.py` re-exports nothing new — callers import the module). allauth.mfa supplies TOTP/recovery primitives behind an encrypting adapter. Session keys carry the pending second factor and the impersonator. Dashboard: login two-step flow, a two-factor card, people-page actions, an app-shell banner, a quick-login page and a security log.

**Tech Stack:** Django 6 + DRF + django-tenants + allauth 65.19 (mfa) + cryptography (Fernet); React + TanStack Router/Query + zod + i18next + vitest + Playwright.

**Spec:** `docs/superpowers/specs/2026-10-03-b9b-sign-in-design.md` (S-0…S-14). Read it before each task. Phase spec: `docs/superpowers/specs/2026-10-03-platform-extras-design.md`.

## Review Focus

1. **An impersonating admin changing the target's credentials by any route** (API or a leftover `/accounts/` page) → 403 / 404 (Tasks 1, 7).
2. **A quick-login link opened twice, or by two tabs at once** → exactly one sign-in (Task 8 `test_concurrent_exchange_signs_in_once`).
3. **Sign-in by phone where two siblings share the parent's phone** → each with their own password signs in; same password → refused, email still works (Task 5).
4. **A user with two-factor whose password is changed between the two steps** → the pending sign-in fails (Task 5 `test_password_change_between_steps_fails`).
5. **The `two_factor` switch turned off** → everyone signs in with password only, authenticators kept, turning it back on restores 2FA (Task 5).

**Mechanics (exact):**

```python
def start(request, actor, target):
    previous_login = target.last_login
    actor_hash = actor.get_session_auth_hash()
    login(request, target, backend="django.contrib.auth.backends.ModelBackend")
    request.session[IMPERSONATOR_KEY] = {"id": actor.pk, "hash": actor_hash, "since": int(time.time())}
    User.objects.filter(pk=target.pk).update(last_login=previous_login)
    SecurityEvent.objects.create(kind="impersonate", actor=actor, target=target, ip=client_ip(request))

def stop(request):
    data = request.session.get(IMPERSONATOR_KEY)
    actor = User.objects.get(pk=data["id"])  # guarded: missing → logout
    target = request.user
    previous_login = actor.last_login
    login(request, actor, backend=...)   # flushes, so the key is gone
    User.objects.filter(pk=actor.pk).update(last_login=previous_login)
    SecurityEvent.objects.create(kind="return", actor=actor, target=target, ip=client_ip(request))
```

`may_impersonate(actor, target) -> str | None` returns a reason or None: actor admin, or staff with `quick_login.create` and `{kind}.view`; target role in teacher/student/parent; parent → `features.enabled("parents")`; `refusal(target)`; `account_state(target) in ("active", "invited")`; not already impersonating. `QuickLoginView` maps a reason to 400 `{"detail", "code": "identity.quick_login_refused"}` (403 for permission reasons via HasCode as usual).

Authentication re-check (in `SessionAuthentication.authenticate` after the existing refusal check): if the session has `IMPERSONATOR_KEY` → load actor; logout and return None when actor missing/inactive, `actor.get_session_auth_hash() != data["hash"]`, actor neither admin nor holding `quick_login.create` (use `codes_of`), `not features.enabled("quick_login")`, or `time.time() - since > 3600`.

- [ ] Tests: permission matrix (admin; staff with both codes; staff missing either → 403; teacher → 403); refused targets (admin, staff, inactive, no_login, parent with parents off, while impersonating) and allowed invited; after start `me.id == target.id`, `me.impersonator == {id, full_name}`; target's `last_login` unchanged and no S-8 fields written; change password / add email / 2FA setup → 403 `identity.impersonating`; re-check log-outs (deactivate actor → `_end_sessions` ends it; actor password change; switch off; 3601 s); stop restores actor `me`, actor `last_login` unchanged; events recorded (2); `impersonator_id` helper and `NotImpersonating` on a dummy view.
